# EventFlow — инструкции Codex

Рабочий блокнот event-менеджера: мероприятия со свободными полями, задачи, календарь и Флуд. Чек-листы остаются дополнительными. Репозиторий `LeSauteur/EventFlow`, remote `origin`, основная ветка `main`.

## Архитектура и данные

- React + TypeScript + Vite: маршруты `src/App.tsx`, исходники `src/`, статические ресурсы `public/`, проверки `tests/` и `scripts/`, описание концепции `docs/NOTEBOOK_WORKFLOW.md`.
- Доступ к localStorage, миграции и backup идут через `src/services/storage.ts`, namespace `eventflow.*`. Не обходить этот слой и не терять пользовательские данные при миграции.
- `data/eventflow-data.json` содержит реальные общие данные и по решению владельца публичен. Изменение кода или инструкций не разрешает менять этот JSON. Токены не публиковать и не включать в backup. QA — только на искусственных данных с перехватом GitHub API.

## Команды и публикация

Node.js 24 в CI. `npm ci`, `npm run dev`, `npm run build`, `npm test`, `npm run preview`; `npm run test:browser` — отдельный синтетический набор, запрещён локально при явном запрете браузера. `.github/workflows/qa.yml` проверяет PR, `.github/workflows/pages.yml` собирает `dist/` и публикует Pages после merge. Изменение только рабочего JSON исключено из запуска через paths-ignore; не обходить этим проверки кода. Адрес: `https://lesauteur.github.io/EventFlow/`.

## GitHub, сеть и сохранность

- Перед изменениями: `git status --short`, текущая ветка, `git remote -v`; получить актуальный `origin/main`, работать в отдельной ветке `codex/`. При dirty/чужой копии — отдельный чистый worktree в новом, предварительно проверенном пути. Не делать pull, stash или commit чужих правок.
- Без отдельного разрешения запрещены reset --hard, clean -fd, force push, удаление материалов и перезапись пользовательских изменений. Менять только явно запрошенные файлы; не включать глобальный AGENTS из Codex Home в проект.
- Основной канал GitHub — Git/HTTPS и `gh`, резерв — прямой API или уже подключённый коннектор. Не переходить в браузер, Edge/Chrome, Computer Use, DevTools или браузерную автоматизацию из-за сетевого сбоя. Браузерная публикация требует отдельного прямого разрешения; явный запрет браузера пользователя соблюдать и при локальном тестировании.
- Различать DNS failure, TCP timeout, TLS/Schannel, EOF/timeout, HTTP 401, HTTP 403 и HTTP 429. EOF не доказывает плохой токен. 401 диагностировать отдельно; 403/429 сверять с правами и `gh api rate_limit`. Не выводить секреты/Authorization; у `gh auth status` скрывать строку Token:. Не удалять credentials и не перевыпускать токен автоматически.
- На Windows сохранять работающий OpenSSL backend. Не отключать SSL verification/отзыв, не использовать curl -k, не менять VPN, DNS, прокси и системные сертификаты. Ошибка Schannel curl не означает отказ Git.
- Максимум две контролируемые попытки одного способа для одной операции; затем сменить канал диагностики (например, GraphQL → REST API), а не повторять бесконечно. Если Git работает — продолжать безопасные Git-операции. Если оба канала недоступны — остановиться с последней успешной операцией, точной ошибкой и handoff. После неясного результата записи сначала проверить состояние. Если push успешен, а PR создать нельзя, сохранить ветку и сообщить это без браузерного обхода.

## Штатный выпуск

Публиковать только по прямой задаче: подходящие локальные проверки → commit только нужных файлов → `git push -u origin <ветка>` → `gh pr create --base main --head <ветка>` → `gh pr checks <PR> --watch --interval 10` → при успешном CI и разрешённом слиянии `gh pr merge <PR> --merge --delete-branch` → безопасное обновление локальной main через `git pull --ff-only origin main` → `gh run list --limit 5` и `gh run watch <ID_RUN_DEPLOY> --exit-status` для точного merge SHA, если предусмотрен deployment. Не пушить напрямую в main, не обходить упавшие проверки, не менять origin и не добавлять deployment remotes/Sites/временный хостинг. Не запускать интерактивную авторизацию; при необходимости входа сообщить точную ошибку.

Если main занята/dirty, сохранить её: fetch и проверка merge в чистом detached worktree вместо переключения чужой копии. При сбое CI читать `gh run view <ID> --log-failed` и исправлять конкретную причину в разрешённом объёме. Не считать merge подтверждением deployment и не запускать повторную публикацию для проверки уже слитого изменения.

Для изменения только документации/AGENTS достаточно проверки содержания, `git diff --check`, точного staged-состава и обязательного CI. Код/данные требуют профильных тестов выше. Запрет браузера пользователя имеет приоритет над ручной UI-проверкой; обязательный CI не отключать, ограничения проверки явно сообщать.
